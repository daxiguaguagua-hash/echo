# 工作流 4: Issue 驱动开发

多步骤变更通过 issue 文档追踪，配合 ECHO_STATUS.md 进度表。内含框架优先的优先级模型。

**类型**: 稳定模式 — issues/001-008 全部存在。

## 触发条件

- 任何需要多个步骤的变更
- 新功能、重构、bug 修复
- 跨模型审查后的设计落地

**不触发**: 小改动/文案/单点修复 — 直接改 + 测试 + 更新 STATUS 即可。

## 优先级模型（框架优先）

```
P0: 数据清理、框架修正     ← 不做会导致后续功能建在错误基础上
P1: 框架建设、核心抽象     ← 不做会导致后续功能需要返工
P2: 发布准备、文档         ← 不做会阻塞分发，但不影响内部正确性
P3: 用户可见功能           ← 可以做，但 P0-P2 先
P4: 增强/优化              ← 锦上添花
```

## 流程

```
1. 设计/审查完成后，创建 issue 文档: issues/NNN-short-description.md
2. Issue 包含:
   - 背景: 为什么做
   - 问题: 当前状态和不足
   - 设计决策: 怎么做，备选方案
   - 实施优先级: P0-P4 排序
   - 跨模型审查记录
3. ECHO_STATUS.md 中添加 - [ ] 条目
4. P0 → P1 → P2 → P3 → P4 顺序执行
5. 完成后:
   - ECHO_STATUS.md: - [ ] → - [x]，刷新日期
   - 过验证门: npm test && npm run all
   - git commit
```

## 实际案例

**Issue 008** 优先级排序:

| 优先级 | 任务 | 结果 |
|--------|------|------|
| P0 | 数据清理 | template 污染发现并修复 |
| P1 | Import provider + manifest + CLI | Codex 106 测试 + 251 全绿 |
| P2 | npm 发布准备 | package.json 修正 |

如果跳过 P0 直接做 P3 评论 UI，会显示 17 篇而非 16 篇 — 框架错误放大到上层。
