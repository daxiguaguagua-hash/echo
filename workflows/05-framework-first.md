# 工作流 5: 框架优先开发

Claude + Codex 协商任务优先级，确保框架正确后再加功能，避免返工。

## 触发条件

- 多个任务需要排序
- 新的子系统设计完成
- 发现数据/框架问题需要先修

## 优先级模型

```
P0: 数据清理、框架修正     ← 不做会导致后续功能建在错误基础上
P1: 框架建设、核心抽象     ← 不做会导致后续功能需要返工
P2: 发布准备、文档         ← 不做会阻塞分发，但不影响内部正确性
P3: 用户可见功能           ← 可以做，但 P0-P2 先
P4: 增强/优化              ← 锦上添花
```

## 流程

```
1. Claude + Codex 各自评估任务列表
2. 按 P0-P4 模型分别打分
3. 交叉对比 → 达成共识的优先级排序
4. 记录到 issue 文档 + ECHO_STATUS.md
5. 严格按序执行：P0 全部完成后再碰 P1
```

## 实际案例

**Issue 008 优先级排序**:

| 优先级 | 任务 | 耗时 |
|--------|------|------|
| P0 | 数据清理：template + registry + example | 5 min |
| P1 | Import provider adapter + manifest | 1.5 hr |
| P1 | echoctl import CLI | 30 min |
| P2 | npm 发布准备 | 10 min |
| P3 | 底部评论输入框 | 未开始 |
| P4 | 进化链 UI | 未开始 |

P0 发现并修复了 template 污染问题 — 如果跳过 P0 直接做 P3 评论 UI，UI 会显示 17 篇文章（含 template）而非 16 篇。

## 关键原则

- **P0 不做完不碰 P1**：框架错误会放大到所有上层功能
- **优先级是 Claude + Codex 共识**，不是单方判断
- **评估时考虑"如果不做会怎样"**：P0 = 会出 bug，P1 = 会返工，P2 = 会阻塞
